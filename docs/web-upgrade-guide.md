# RAGFlow Web 二开版本升级手册

## 1. 目标与边界

本项目的 `web/` 基于 RAGFlow 官方前端做了整体换肤、iframe 嵌入和导航改造。后续升级应同时满足：

1. 完整引入官方新版本的 Web 功能和修复。
2. 保留现有视觉设计、页面结构和 iframe 交互边界。
3. 通过可复查的文件清单收尾，不凭印象挑选代码。

默认升级范围是 `web/`。Docker 基础镜像、启动脚本和配置版本只做必要对齐，不在前端升级中顺手改造后端。

## 2. 必须使用三方对比

每次升级同时准备：

- `BASE`：本地二开开始时的官方版本。
- `UPSTREAM`：本次要升级到的官方版本。
- `CUSTOM`：当前项目中的定制 Web。

例如：

```text
BASE      = infiniflow/ragflow v0.26.0
UPSTREAM  = infiniflow/ragflow v0.26.1
CUSTOM    = 当前仓库 web/
```

三组对比各自回答：

- `BASE -> UPSTREAM`：官方这次改了什么。
- `BASE -> CUSTOM`：我们原来定制了什么。
- `UPSTREAM -> CUSTOM`：升级后还保留了哪些有意差异。

只比较 `CUSTOM` 与 `UPSTREAM` 会混淆旧代码和有意定制，不可省略 `BASE`。

## 3. 标准升级流程

### 3.1 保护工作树

先记录升级前已有的未提交改动，不覆盖用户代码：

```bash
git status --short
```

明确记录本地 Web 的官方起点 tag，不要从当前 Docker 镜像版本反推。

### 3.2 建立官方唯一变更清单

```bash
git diff --name-status <OLD_TAG>..<NEW_TAG> -- web
git diff --stat <OLD_TAG>..<NEW_TAG> -- web
```

第一条命令的结果就是升级清单。新增、修改、删除的文件都必须逐项处理，不能只搜索某个新功能名称。

### 3.3 按变更类型合并

#### 功能逻辑：以官方新版本为准

以下内容原则上完整同步：

- API 地址和 service 请求。
- hooks、数据结构和类型定义。
- 表单字段、默认值和校验规则。
- 路由枚举、页面入口和权限分支。
- 状态、异常、删除、导入和导出逻辑。
- `package.json`、lockfile、Jest/Vite 中的官方升级。

#### 纯视觉变更：保留本项目设计

可按现有风格调整：

- `className`、颜色 token、圆角、阴影和间距。
- 页面外层容器、面包屑和 iframe 布局。
- 图标与头像表现。
- 路由加载动画和页面进入效果。

#### 混合文件：逐个变更块处理

1. 先阅读 `BASE -> UPSTREAM` 的官方 patch。
2. 完整带入新的 import、props、数据流和分支逻辑。
3. 再将 JSX 外层和样式合并到本项目设计体系。
4. 不要以“页面能打开”代替逻辑对比。

### 3.4 逐文件对账

升级后的每个官方变更文件必须归入三类之一：

- `EXACT`：本地与官方新版本完全一致。
- `INTENTIONAL_DIFF`：官方功能已带入，只保留有记录的本地设计。
- `MISSING_OR_UNREVIEWED`：文件缺失或差异尚未解释，不得交付。

至少执行：

```bash
git diff --name-status <OLD_TAG>..<NEW_TAG> -- web
git diff --check
```

然后遍历官方清单，确认新版文件在本地是完全一致还是有意差异。有意差异需再对照官方 patch，确保业务变更块已经存在。

## 4. 验证清单

### 4.1 代码验证

```bash
cd web
npm ci
npm run build
```

如官方新增单元测试，应同步测试配置并运行相应用例。如全量 TypeScript 或 lint 存在历史问题，要把历史问题与本次新增问题分开记录。

对官方新增或修改的 i18n key，还需比较主语言资源的命名空间和嵌套结构。页面直接显示 `knowledgeConfiguration.xxx` 一类文本，通常表示当前语言缺键、keyPrefix 不一致或嵌套层级错误。

### 4.2 Docker 点击验证

1. 新增入口能否从 Dashboard 打开。
2. 列表、创建、编辑、删除、关联等主链路是否可用。
3. 表单默认值和密码字段回显是否正确。
4. 新页面是否符合现有颜色、圆角、面包屑和 iframe 边界。
5. 路由进入、刷新、返回和直接 URL 访问是否正常。
6. 浅色/深色主题和中英文文案是否正常。

## 5. 前后端边界判断

遇到“后台有报错，前端没显示”时，先检查：

1. 请求是否收到非成功 code/message。
2. 查询接口是否返回运行状态或错误字段。
3. 官方新版 Web 是否确实消费该字段。

如果错误只发生在服务端异步线程，且 API 没有返回，Web 无法凭空展示它。这应记为独立的前后端增强需求，不应误判为 Web 升级漏文件。

## 6. v0.26.0 -> v0.26.1 对账记录

- 官方 `web/` 变更文件：99 个。
- 与官方 v0.26.1 完全一致：81 个。
- 保留有意差异：18 个。
- 缺失文件：0 个。
- 18 个差异集中在皮肤、页面外层、头像、用户设置导航、路由过渡和开发代理适配。
- 聊天渠道的 service、hooks、表单提交和编辑逻辑与官方一致；频道页面仅做了本项目的视觉包装。
- QQBot `appid invalid` 是官方后台线程在保存成功后异步产生的日志，v0.26.1 API 没有将该运行错误暴露给 Web，不属于漏同步的前端逻辑。

## 7. 完成标准

- 官方 Web 变更清单中没有缺失或未审查项。
- 所有与官方不一致的文件都能说明原因。
- 业务逻辑与官方新版本对齐。
- 新页面已适配本项目的视觉和 iframe 布局。
- 生产构建通过，新增测试已运行或明确记限制。
- Docker 点击验证的主链路结果已记录。
